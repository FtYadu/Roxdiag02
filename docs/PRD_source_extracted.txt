1. Executive Summary

The ROX Offline Diagnostic Suite is a professional, self-contained Windows desktop

application for automotive workshops, fleet maintenance, and independent repair shops

servicing the R11_Oversea platform. It delivers full diagnostics, guided special functions,

and secure MCU reflashing with no internet connection required.

The suite consumes the OEM data package directly — the  R11_Oversea.xml  vehicle profile,

the per-ECU folder tree, the XML flow scripts, and the reflash sequences — and translates

OEM-defined procedures into wizard-style workflows driven by a built-in flow interpreter.

Security material (seed-key) is executed locally through a pluggable module the user

supplies; no OEM cryptographic algorithms are embedded in the application, keeping it

compliant with OEM tool policy and legally clean.

The platform being serviced is not an ordinary car. Its architecture — dedicated

autonomous-driving controller with its own MCU ( ADCU / ADCU_MCU ), four corner radars

( SRR_FL/FR/RL/RR ) plus front radar ( MRR_F ), an automotive-Ethernet/DoIP backbone, and

redundant electric steering ( EPS  +  EPS_FD ) — is the signature of an L2++/L3 autonomy

design. This raises the stakes on reflashing and security-gated writes and shapes the safety

requirements in §13.

The application serves both novice technicians (guided workflows) and expert engineers

(raw-UDS console).

2. Product Scope and Objectives

2.1 In-Scope

Reading and clearing DTCs across all ECUs, with automatic read-back verification and

live-fault detection.

Executing guided special functions via the flow engine: IMMO key add/delete, key

pairing, key duplication, VIN writing, config-word writing, IMMO security-constant

writing, TPMS matching, window/sunroof self-learning, ECU reset.

MCU firmware reflashing with chunked download sized from the ECU’s declared block

length, response-pending handling, checksum/CRC verification, and error recovery.

Automatic ECU discovery and vehicle-profile loading from  R11_Oversea.xml  and the

ECU folder tree.

CAN (ISO 15765, with ISO-TP segmentation) and DoIP (ISO 13400, with routing

activation) transport.

Offline security access via a user-supplied local seed-key module (DLL or script)

through a defined call boundary.

Guided GUI plus an expert raw-UDS console.

Session logging, audit trail, and reporting.

2.2 Out-of-Scope (this version)

Online cloud services, VIN decoding, or vehicle-history lookup.

Vehicle platforms other than R11_Oversea (architecture is XML-driven, so future profiles

are additive — see NFR Scalability).

Wireless (Bluetooth/Wi-Fi) communication — wired OBD-II only.

Oscilloscope / live-parameter graphing beyond DTC and DID reads.

Multi-vehicle simultaneous diagnostics.

Accuracy — correctly interpret every OEM-defined UDS service and flow-control

5. Flow Engine Specification (Reverse-Engineered

FlowConfiguration  Schema)

This section is the authoritative reference for the flow interpreter. It is split into observed

(directly evidenced from the flow fragment) and reconstructed (inferred from standard

guided-function engine design and flagged as such). Confirm the reconstructed request-

side names against one complete flow file before freezing the parser (§17).

5.1 Element Containment (observed)

Innermost → outermost, exactly as seen:

LeftValue  @IsVariable @Value

OpSign     @Value

RightValue @IsVariable @Value

ConnectSign @Value

  → OneCondition → Condition → If @Description

    → ChildStep → EcuService → ChildStep → Process → Processes → FlowConfiguration

Confirmed attribute facts:

LeftValue  /  RightValue :  IsVariable  (boolean) +  Value .

OpSign   @Value : comparison operator;  Equal  observed (enum:  Equal | NotEqual |

Greater | Less | GreaterOrEqual | LessOrEqual , reconstructed).

ConnectSign   @Value : boolean join;  OR  observed ( AND  reconstructed).

If   @Description : label attribute; empty is written as the literal string  "null" .

ResponseStatus : a built-in runtime variable the engine populates after each

EcuService .

5.2 Reconstructed Full Tree

FlowConfiguration                        [root]

└─ Processes                             [container]

   └─ Process            [1..n]          one guided function

      ├─ @Name / @Description            (reconstructed)

      └─ ChildStep       [1..n, RECURSIVE — steps nest steps]

         ├─ @Description                 ("null" pattern)

         ├─ EcuService   [0..1]          one UDS transaction

         │  ├─ @Ecu / @Target            target module (reconstructed)
         │  ├─ «REQUEST SIDE»            ⚠ not in fragment — must exist

         │  │   ├─ ServiceId             0x27 / 0x2E / 0x31 / 0x22 …

         │  │   ├─ SubFunction

         │  │   └─ RequestData / DID     from variables or literals

         │  └─ ChildStep                 response handling

         │     └─ If @Description

         │        ├─ Condition

         │        │  └─ OneCondition [1..n, joined by ConnectSign]

         │        │     ├─ LeftValue   @IsVariable @Value

         │        │     ├─ OpSign      @Value

         │        │     ├─ RightValue  @IsVariable @Value

         │        │     └─ ConnectSign @Value
         │        └─ «THEN / ELSE body» ⚠ reconstructed

         └─ «other step types»           ⚠ reconstructed — see 5.5

5.3 Execution / Variable Model

The engine maintains a runtime key-value store.  IsVariable="true"  means “resolve

Value  against the store at execution time”;  false  means literal.

ResponseStatus  is the first confirmed reserved system variable. Others the engine

must maintain: last raw response, last NRC, session state, security state, extracted

operands (e.g.  seed ,  keyCount ).

After every  EcuService , the engine writes  ResponseStatus  (and the raw response)

before evaluating that service’s response-side  If  blocks.

5.4 Two Parser Rules (both derived from the observed fragment)

1. Trailing  ConnectSign  is a no-op. The editor emits  ConnectSign  on every

OneCondition , including the last one in a  Condition , where it has no following sibling.

The parser must not let a trailing join dangle into the next node.

2. Consecutive- If  = OR-set of acceptable states. The fragment contains back-to-back

If  blocks testing  ResponseStatus Equal 2 , then  Equal 3 . This is the acceptance

idiom: rather than one  If  with ORed conditions, the tool emits one  If  per acceptable

response state. Treat  ResponseStatus ∈ {2,3}  as “service accepted, continue.”

5.5 Node Types the Interpreter Must Add (beyond  EcuService  +  If )

The observed file exposed only the response/condition tail. Real key and reflash flows

require:

SecurityAccess node — a specialised  EcuService  that emits  27 <odd> , routes the

seed to the external security module, and returns  27 <even> <key> . Single most

important new node.

UserPrompt node — blocking operator interaction (“insert key”, “cycle ignition”,

“remove key within N s”) with a timeout.

Assign / Extract node — the write side of the variable store: pull specific bytes from a

response into a named variable ( seed ,  keyCount ,  sessionState ).

Loop node — iterate the ECU list (DTC scan) and poll the pending state ( 31 03 …  until

the routine reports complete).

An interpreter handling only  EcuService  +  If  will parse the simple flows and fail on the

key/reflash flows.

5.6 ResponseStatus Enum — Hypothesis, Not Confirmed

Because the flow accepts  2  and  3  (not  0 / 1 ), the encoding is likely not the naïve  0 =

OK . Working hypothesis:  1 = negative/NRC ,  2 = positive response ,  3 = positive-with-

pending-resolved (0x78 cleared) . This must be confirmed from a complete flow — the

reflash flow will settle it, since a RequestDownload/TransferData sequence has to loop

explicitly on the pending state. Tracked in §17.

7. Security Architecture

Posture (unchanged and deliberate): the application embeds no OEM seed-key

algorithm. Security is executed by a user-supplied module the operator is licensed to hold.

This keeps ROX compliant with OEM tool policy.

7.1 The Call Boundary

The flow’s SecurityAccess node (§5.5) is the only place security material crosses the

boundary:

Flow (SecurityAccess node)

   │  27 <odd> requestSeed  ──────────────►  ECU

   │  67 <odd> <seed>       ◄──────────────  ECU

   │  seed  ──────────►  [ Security Module ]     (external DLL / script)

   │  key   ◄──────────  ComputeKey(seed[], length) : key[]

   │  27 <even> <key>       ──────────────►  ECU

   │  67 <even>             ◄──────────────  ECU  (access granted)

Interface: exported  ComputeKey(seed, length) -> key , called via P/Invoke.

The interpreter never computes the key; it only marshals seed out and key back.

keyCount  / routine IDs / DIDs used by pairing, duplication and deletion are data-

package values, not application logic.

7.2 Controls

Licence check — offline licence-key validation to prevent unauthorised use.

Secure storage — security-module path stored via Windows DPAPI (encrypted).

Audit trail — every security-gated operation (0x27, key write/delete, VIN write, reflash)

logged with timestamp, operation, ECU, and result. No plaintext keys or full seeds in

logs (FR-08.4).

No network egress — verified in an isolated network.

8. Transport Layer Specification

Resolves the v1.0 C#/ python-can  inconsistency: the stack is .NET, and CAN uses vendor

driver APIs via P/Invoke — not  python-can .

8.1 CAN (ISO 15765)

Interfaces via vendor APIs (PCAN-Basic, Kvaser CANlib, or Vector XL Driver) through

P/Invoke.

ISO-TP (ISO 15765-2) is mandatory: DTC lists, DIDs and flash blocks exceed a single

8-byte frame, so the transport must implement First/Consecutive frames, Flow-Control

frames, and honour BlockSize and STmin. Block-sequence and padding handled at this

layer, below the UDS client.

Default 500 kbps (from  R11_Oversea.xml ), channel selectable.

8.2 DoIP (ISO 13400)

Raw TCP sockets ( System.Net.Sockets ), default port 13400, over the DoIP pins

(activation line = pin 8).

Routing-activation handshake required before UDS: optional vehicle-

announcement/identification (0x0004), then routing-activation request (0x0005) →

response (0x0006). Diagnostic messages are payload type 0x8001 with 0x8002 (ack) /

0x8003 (nack).

Manual IP/subnet/gateway or DHCP (FR-02.2).

The Transport Abstraction Layer exposes one interface to the UDS client

( SendRequest(bytes) → response bytes ), hiding CAN-vs-DoIP so flows and the UDS client

are transport-agnostic.

4. If security is required, route via the security module or prompt for a key.

5. App re-reads and flags any code that re-sets immediately as a live fault.

6. Show “DTCs cleared (N stale cleared, M live remaining)”.

UC-02: Execute a Special Function Flow (corrected)

Actor: Service Technician. Precondition: vehicle connected, flow XML available.

2. App parses the flow to an AST and shows the first instruction.

3. Technician follows prompts (e.g. “Insert new key, ignition ON”).

4. App executes UDS requests per flow, resolving variables and evaluating conditions.

5. Continue on  ResponseStatus ∈ {accepted set}  (observed:  {2,3} ); on a value outside

the accepted set, follow the flow’s failure path (retry/abort). (v1.0 wrongly hard-coded

UC-03: Perform MCU Reflash

Actor: Diagnostic Engineer. Precondition: vehicle connected, firmware ready, battery

maintainer attached.

1. Open Reflash, select target ECU, load firmware.

2. App loads the reflash flow and shows pre-flash warnings; engineer confirms.

3. App runs pre-flash steps:  10 02/03 ,  85 02  (DTCs off),  27  security, precondition +

erase routines.

4. Sends  0x34 , reads  maxNumberOfBlockLength  from the response.

5. Streams  0x36  blocks (sequence-counted), auto-waiting on 0x78; progress +

throughput shown.

6. Sends  0x37 , runs checksum/ checkMemory  routine.

7. Shows “Reflash successful” or detailed error; logs with checksum.

Actor: Service Technician / locksmith. Precondition: vehicle connected, security module

1. Open Key Functions → Pairing.

2. App runs  10 03  → SecurityAccess (seed→module→key) → reads current  keyCount .

3. Prompts “Insert new key, ignition ON”.

4. Runs the learn routine ( 31 01 … ), polling  31 03 …  while pending.

11. System Architecture (High-Level)

Modules:

1. Profile Manager — loads  R11_Oversea.xml  + ECU folders, builds the internal registry.

2. Transport Abstraction Layer — CAN (ISO-TP over vendor API) and DoIP (routing-

activated sockets) behind one interface (§8).

3. UDS Client — builds requests, parses responses, decodes NRCs (§6).

4. Flow Engine — parses flow XML → AST, executes step-by-step, evaluates conditions,

substitutes/extracts variables, runs the node types in §5.5.

5. Reflash Controller — extends the Flow Engine with block sizing (from 0x34), sequence

counting, progress, CRC.

6. Security Provider — loads the user-supplied module, marshals seed/key across the

boundary (§7), caches session state.

7. GUI (WPF) — guided workflows, expert console, logging, reporting.

8. Logger — structured logs + audit trail to disk.

Data flow:

User → GUI → FlowEngine/ReflashController → UDSClient → Transport → Vehicle

Vehicle → Transport → UDSClient → FlowEngine → GUI

                                   │

                          SecurityProvider (seed↔key, on 0x27)

Technology stack:

Language: C# (.NET 6), for robust Windows desktop + XML handling.

CAN: vendor driver API (PCAN-Basic / Kvaser CANlib / Vector XL) via P/Invoke; ISO-TP

implemented in-app or via the vendor’s ISO-TP layer.

DoIP:  System.Net.Sockets  with a DoIP state machine.

XML:  System.Xml  /  System.Xml.Linq .

Config:  System.Text.Json  (or Newtonsoft) for  settings.json .

Dialogs: Ookii.Dialogs for file/folder pickers.

Build: self-contained single executable (.NET); AOT optional (note: AOT + P/Invoke to

vendor DLLs is supported, validate per driver).

13. Testing & Validation Strategy

Because the platform includes safety-critical ECUs (ADCU_MCU, ACU airbag, dual

EPS / EPS_FD ) and irreversible operations (key delete, VIN write, reflash), validation is a

first-class requirement, not an afterthought.

Bench / restbus simulator — a UDS/ECU simulator (or restbus) for developing and

regression-testing DTC, flow-engine, security-boundary and reflash logic without a live

vehicle. Mandatory for CI of the core modules.

Flow-engine unit tests — cover the two parser quirks (§5.4), variable

resolution/extraction, condition grouping, and the pending-poll loop, using captured flow

XML.

Golden traces — record real request/response traces and replay them to detect

regressions in UDS/NRC handling.

Reflash safety gate — reflash blocked below a configurable battery-voltage threshold;

require a battery-maintainer confirmation; validate 0x78 looping and block-sequence

wrap on the simulator before any live flash.

Key-function dry run — verify key-count read-back and lockout handling (0x36/0x37)

on the simulator before enabling on a vehicle.

Destructive-op confirmations — automated tests that every irreversible operation is

gated behind explicit confirmation and produces an audit entry.

Appendix A — Glossary

UDS — Unified Diagnostic Services (ISO 14229)

ISO-TP — ISO 15765-2 transport (multi-frame CAN segmentation)

DoIP — Diagnostics over IP (ISO 13400)

DTC — Diagnostic Trouble Code

DID — Data Identifier (0x22/0x2E operand)

NRC — Negative Response Code

RoutineControl — UDS 0x31 (start/stop/results)

RequestDownload / TransferData / TransferExit — UDS 0x34 / 0x36 / 0x37 reflash

sequence

maxNumberOfBlockLength — max transfer block size, returned in the 0x34 response

Seed-Key — SecurityAccess (0x27) handshake

SecOC / SK — Secure Onboard Communication key material (“SK Brush Write”)

IMMO — Immobilizer

AST — Abstract Syntax Tree (flow parsing)

ADCU / ADCU_MCU — Autonomous Driving Control Unit and its dedicated MCU

SRR / MRR — Short-/Mid-Range Radar (corner and front ADAS sensors)

EPS / EPS_FD — Electric Power Steering and its redundant/failover unit

Appendix B — Reverse-Engineered Schema Quick Reference

FlowConfiguration → Processes → Process → ChildStep(recursive)

  ChildStep may contain:

    EcuService  { request: SID/SubFunction/Data;  response: ChildStep → If … }

    If @Description → Condition → OneCondition[1..n]

        OneCondition: LeftValue@IsVariable@Value  OpSign@Value

                      RightValue@IsVariable@Value ConnectSign@Value

    (to add) SecurityAccessNode, UserPromptNode, AssignNode, LoopNode

Rules:

  • trailing ConnectSign = no-op

  • consecutive If on same var/different literals = OR-set of accepted states
  • IsVariable="true" ⇒ resolve against runtime store; ResponseStatus is reserved
